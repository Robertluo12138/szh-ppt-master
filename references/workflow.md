# Workflow

The skill is a single linear pipeline. Stages are append-only; do not skip or reorder.

| # | Stage | Input | Output | Schema |
|---|---|---|---|---|
| 1 | Intake | local Markdown / text source file (`--source`) | `<workspace>/input/source.md` + `<workspace>/source_manifest.json` (written by `scripts/init_workspace.py`; this script does NOT plan a deck and does NOT generate any later-stage artifact) | `schemas/source_manifest.schema.json` |
| 2 | Brief | normalized source | `deck_brief.json` (Stage-2 contract helper `scripts/init_deck_brief.py` writes only the schema-required skeleton — `title`/`audience`/`objective` from explicit `--title`/`--audience`/`--objective` flags plus `source_refs = [source_manifest.source.id]` — and never extracts business content from `input/source.md`; it does NOT plan a deck) | `schemas/deck_brief.schema.json` |
| 3 | Plan | `deck_brief.json` | `deck_plan.json` (adaptive length, structure, layouts, density; Stage-3 contract helper `scripts/init_deck_plan.py` validates a caller-supplied `--plan-spec` JSON file against the schema + planner-semantics cross-checks and writes the result — it does NOT extract business content from `input/source.md` and is NOT a full prompt/report-to-PPTX automation) | `schemas/deck_plan.schema.json` |
| 4 | Design system | `deck_plan.json` + template | `design_system.json` (Stage-4 contract helper `scripts/init_design_system.py` validates a caller-supplied `--spec <design_system.json>` OR projects palette / typography / grid from `--theme-from-template` + `--template-root <dir>` resolved through `deck_plan.template`, validates the candidate against the schema, and writes the result — the helper itself never opens `input/source.md` (it invokes the Stage-1/Stage-2 bridge, which reads the source bytes only for byte-level integrity checks: UTF-8 decode validity, byte_count / line_count / sha256 match against the manifest), does NOT infer design from raw source text, has no hardcoded template default, and is NOT a full prompt/report-to-PPTX automation) | `schemas/design_system.schema.json` |
| 5 | Per-slide plan | `deck_plan.json` + `design_system.json` | one `slide_plan.json` per slide (Stage-5 contract helper `scripts/init_slide_plans.py` writes the canonical `<workspace>/slide_plans/<idx:02d>_<layout>.json` set from a caller-supplied `--specs-dir` of slide_plan JSON candidates, validating each against the schema + cross-checking against `deck_plan.slides[]` 1:1 by `index` + matching `layout` / `title` + covering required layout slots — it does NOT extract business content from `input/source.md`, does NOT infer slide content from raw source text, and is NOT a full prompt/report-to-PPTX automation) | `schemas/slide_plan.schema.json` |
| 6 | Image manifest | per-slide plans | `image_manifest.json` (Stage-6 contract helper `scripts/init_image_manifest.py` validates a caller-supplied `--spec` JSON file against the schema, refuses duplicate `images[].id` and unsafe `local_path`, requires every `local_path` to resolve inside the workspace to a regular non-symlink file, and cross-checks every `slide_plan.image_refs` id against `images[].id` — it does NOT generate any image asset, never opens `input/source.md`, never calls D-One / Qoder / any public network, and is NOT a full prompt/report-to-PPTX automation. The downstream **D-One adapter contract STUB** `scripts/done_image_adapter.py` reads the manifest plus a caller-supplied `--spec <prompt-spec.json>` of safe prompts, refuses every request whose `id` does not match a manifest entry with `source == "d_one_local"` and every prompt that contains URIs / file paths / raw-source markers / 40-char source shingles / credential shapes / customer-account-contact ids / full-slide / page-generation / screenshot wording, and writes a deterministic dry-run plan to `<workspace>/d_one_adapter_plan.json` whose shape is locked by `schemas/d_one_adapter_plan.schema.json` (strict `additionalProperties: false`; `mode` enum-locked to `"dry_run"`; `schema_version` enum-locked to integer `1`; `manifest_source` enum-locked to `"d_one_local"`; post-write `_schema_validate` step rolls back on failure). The same plan schema also drives the non-mutating `done_image_adapter.py --validate-plan --workspace WS --plan PATH` mode, which re-runs the schema + the manifest cross-checks + the full prompt safety scan against an existing plan file — it does NOT call D-One / any image-generation model / any public network, does NOT generate any image bytes, does NOT change PPTX export behavior, and is NOT real D-One integration) | `schemas/image_manifest.schema.json` + `schemas/d_one_adapter_plan.schema.json` |
| 7 | Render model | per-slide plan + design_system + image_manifest + layout slots | one `render_model.json` per slide (controlled primitives, bounds, token-only style refs) | `schemas/render_model.schema.json` |
| 8 | SVG render | per-slide render model | one SVG preview per slide under `svg_previews/` (partial: `text`, `line`, `shape`, `image_slot`, `kpi`, `table`) | XML; controlled by `check_svg_previews` in `scripts/validate_workspace.py` |
| 9 | SVG validate | per-slide SVG | pass/fail against `check_svg_previews` | implemented (repair: TODO) |
| 10 | PPTX export | per-slide render model | one editable PPTX (native shapes / text frames / connectors / tables) | partially implemented — `scripts/export_pptx.py` exports the supported subset (layouts `cover`, `kpi_dashboard`, `agenda`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `timeline`, `conclusion`, `comparison_table`; primitives `text` / `line` / `shape` / `image_slot` / `kpi` / `table`); `scripts/validate_pptx_contract.py --pptx` runs the container + minimal-evidence safety/editability gates against the result (including `relationships.allow_list` and `minimal_evidence.every_slide_has_native_shape`); everything outside that scope still fails closed |
| 11 | Reports | PPTX + artifacts | security / editability / visual reports | TODO |

Stage 1 → 2 is gated by an **intake bridge** the validators apply when a workspace ships `source_manifest.json` as a **regular in-workspace file** — a symlink at that path (broken or resolvable) is refused outright by a symlink preflight that runs BEFORE `_try_load` / `read_text`, so neither a dangling link masquerading as the legacy "no manifest" no-op nor a resolvable link reading manifest bytes from outside the workspace can slip through. `scripts/validate_workspace.py` and `scripts/validate_scaffold.py` each invoke `check_source_manifest_bridge` (see `source_manifest.bridge` in `references/quality-gates.md`) which applies the symlink preflight first, then schema-validates the manifest, confirms `source.local_path == "input/source.md"` resolves inside the workspace and exists as a regular UTF-8 file whose `byte_count` / `line_count` / `sha256` match the on-disk source, and confirms `source.kind` is one of the schema-documented values (`markdown` for a .md-original source, `text` for a .txt-original source — `init_workspace.py` normalizes the on-disk filename to `input/source.md` regardless of the original extension, so both kinds are legitimate against the canonical filename). When `deck_brief.json` is present, `deck_brief.source_refs` must declare `source_manifest.source.id`. A Stage-1-only workspace (manifest + source.md, no `deck_brief.json`) is valid by design: the bridge passes every on-disk row and skips the deck_brief cross-check row rather than emitting a FAIL. Workspaces without `source_manifest.json` are a no-op so prepared examples that pre-date `init_workspace.py` remain valid. The bridge is verification-only — it does NOT plan a deck, mutate the workspace, or run any prompt-to-deck automation.

The Stage-1 → Stage-2 *producer* side is automated, narrowly, by `scripts/init_deck_brief.py`: given a workspace that already passes the intake bridge (Stage 1 complete) plus explicit `--title` / `--audience` / `--objective` flags, the helper writes a minimal, schema-valid `deck_brief.json` whose `source_refs` is exactly `[source_manifest.source.id]`. **This is Stage-2 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper does not extract business content from `input/source.md`, does not invent `key_messages` / `constraints` / `tone` / `language` / `approximate_slide_count` when the caller does not pass them, does not plan a deck, and emits no artifact other than `deck_brief.json`. The brief is schema-validated in memory before any write and re-validated on disk afterwards; a post-write re-validation failure rolls the brief back. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s SystemExit branch on read-errors still routes through rollback. `--self-test` exercises 29 in-script tempfixture scenarios under `tempfile.TemporaryDirectory()`, including the symlink preflight at `source_manifest.json` for both a broken and a resolvable link (proving `read_text` / the bridge cannot follow either to read manifest bytes from outside the workspace, and that no `deck_brief.json` is written when either case is detected), the symlink-first guard at `deck_brief.json` for both a broken and a resolvable link (proving `write_text()` cannot follow either and clobber an unrelated target), a marker-phrase test that proves the source body is never copied into the brief, and a mutated-brief test that proves the bridge catches a `source_refs` that drops `source.id`. Stages 3–6 (`deck_plan.json`, `design_system.json`, `slide_plans/*.json`, `image_manifest.json`) remain agent-driven beyond the narrow contract helpers — Stage 3 has the narrow contract helper described next, Stage 4 has its own narrow contract helper described after that, Stage 5 has its own narrow contract helper via `scripts/init_slide_plans.py` (caller supplies `--specs-dir` + `--template-root`; `init_deck_plan.py` and `init_design_system.py` do NOT themselves generate any slide_plans); Stage 6 has its own narrow contract helper via `scripts/init_image_manifest.py` (caller supplies `--spec`; the helper validates against the schema and cross-checks every `slide_plan.image_refs` against `images[].id`, but does NOT generate any image asset, call D-One / Qoder / any public network, or extract source content).

The Stage-2 → Stage-3 *producer* side now has narrow contract support via `scripts/init_deck_plan.py`: given a workspace that already passes the intake bridge AND ships a schema-valid `deck_brief.json`, plus a `--plan-spec` JSON file whose shape is exactly the deck_plan candidate the caller wants written, the helper validates that spec against `schemas/deck_plan.schema.json` and the planner-semantics cross-checks (`planning.planned_slide_count == len(slides)`, slide indices unique + contiguous 1..N, section coverage 1:1 with deck_plan slides, every `slide.section_id` resolves to a declared section, every `slide.source_refs` value is declared in `deck_brief.source_refs`) and writes the result deterministically to `<workspace>/deck_plan.json`. **This is Stage-3 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper does not read or parse `input/source.md`, does not invent `template` / `rationale` / `slides` / `sections` content when the caller does not pass them, does not plan a deck, and emits no artifact other than `deck_plan.json`. The Stage-3 source_refs contract has four parts: (1) `deck_brief.source_refs` is the required allow-list of source ids for the deck; (2) `deck_plan.json` carries source_refs only on its per-slide entries (`slides[].source_refs`) — there is no document-root source_refs field on the plan (the schema declares none and `additionalProperties: false` would refuse one if added); (3) deck_plan lineage is per-slide only — every `slides[].source_refs` must be non-empty and a subset of `deck_brief.source_refs`; (4) the bridge gate places `source_manifest.source.id` in `deck_brief.source_refs`, but that does not imply every slide cites `source_manifest.source.id` — when the brief declares multiple ids, a slide may legitimately pick another id from the allow-list. The plan is schema-validated in memory before any write and re-validated on disk afterwards; a post-write re-validation failure rolls the plan back. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s SystemExit branch on read-errors still routes through rollback. `--self-test` exercises 29 in-script tempfixture scenarios under `tempfile.TemporaryDirectory()`, including the positive happy paths (1-slide / 3-slide), determinism between two independent runs, missing `deck_brief.json` (no silent fallback), malformed deck_brief, a deck_brief whose `source_refs` omits `source_manifest.source.id` (refused at the bridge), `planned_slide_count` mismatch, duplicate slide indices, **non-contiguous slide indices** ([1, 2, 4]), section coverage that omits a slide, section coverage that lists an orphan slide_index, an unknown `slide.section_id`, a `slide.source_refs` value not declared in `deck_brief.source_refs`, the no-source_manifest legacy workspace (refused — the existing prepared examples that pre-date `init_workspace.py` simply do not run this helper), a pre-existing regular-file `deck_plan.json` (refused with prior bytes preserved), broken / resolvable symlink at `deck_plan.json`, broken symlink at `source_manifest.json`, a `--plan-spec` that is a symlink / malformed JSON / list-rooted / schema-invalid, missing / regular-file / URI-shaped `--workspace`, a marker-phrase test that proves the source body is never copied into the plan, and mocked post-write rollback (return errors / raise `SystemExit`). After `init_deck_plan.py` succeeds, Stage 4 has narrow contract support via `scripts/init_design_system.py` (described below; that helper does NOT itself generate any slide_plans); after that, Stage 5 has narrow contract support via `scripts/init_slide_plans.py` (caller supplies `--specs-dir` + `--template-root`); after that helper succeeds, Stage 6 (`image_manifest.json`) has narrow contract support via `scripts/init_image_manifest.py` (caller supplies `--spec`) before `scripts/run_pipeline.py` can take over for stages 7–10.

The Stage-3 → Stage-4 *producer* side has narrow contract support via `scripts/init_design_system.py`: given a workspace that already passes the intake bridge AND ships schema-valid `deck_brief.json` + `deck_plan.json`, plus EXACTLY ONE explicit caller input — either `--spec <design_system.json>` (a complete design_system the caller wants validated and written verbatim) OR `--theme-from-template` + `--template-root <dir>` (project palette / typography / grid from the theme of the template named in `deck_plan.template`, resolved against the supplied template root) — the helper re-validates `deck_brief.json` and `deck_plan.json` against their schemas AND runs EXACTLY the planner-semantics cross-checks `init_deck_plan.py` applies before writing a Stage-3 artifact (re-using `init_deck_plan._cross_check_planner_semantics` — planned-count equality, slide indices unique AND contiguous 1..N, section coverage 1:1, slide.section_id resolution, slide.source_refs subset of deck_brief.source_refs) so a deck_plan `init_deck_plan.py` would not have written is refused before Stage-4 advances. The candidate design_system is validated against `schemas/design_system.schema.json` (hex-coded palette colors, CSS-style font fallback chains, positive numeric font sizes, positive integer grid dimensions, non-negative integer margin) in memory and re-validated on disk, rolling back on failure. **This is Stage-4 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper itself never opens `input/source.md` (it invokes the Stage-1/Stage-2 bridge, which reads the source bytes only for byte-level integrity checks: UTF-8 decode validity, byte_count / line_count / sha256 match against the manifest, and discards the decoded string), does not infer palette / typography / grid from raw source text (tokens come exclusively from `--spec` or the explicitly named template theme), does not produce any artifact other than `design_system.json`, and emits no `slide_plans/*.json` / `image_manifest.json` / render_models / SVG / PPTX. Template resolution is anchored on `deck_plan.template` only; there is no product-level template default — the name `business_review` is just the template the current repo ships, not a fallback. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s SystemExit branch on read-errors still routes through rollback. `--self-test` exercises in-script tempfixture scenarios under `tempfile.TemporaryDirectory()` covering: happy path (both modes), determinism (both modes), missing / malformed / schema-invalid `deck_plan.json`, schema-valid-but-semantically-invalid `deck_plan.json` (planned_slide_count mismatch, broken section coverage, undeclared slide.source_refs, duplicate slide indices `[1, 1]`, non-contiguous slide indices `[1, 2, 4]`, unknown `slide.section_id` — all refused at the planner-semantics cross-check via the same gate `init_deck_plan.py` applies), missing `deck_brief.json`, unknown template (no business_review fallback), unsafe template path (`..` and URI scheme), missing theme file, missing / malformed / list-rooted / schema-invalid `--spec` (bad hex color, empty font_family, non-positive grid width, negative margin), pre-existing `design_system.json` refused with prior bytes preserved, broken / resolvable symlink at `design_system.json` refused with target preserved, symlink at `--spec` / theme file / `--workspace` refused, URI-scheme `--workspace` refused, mutually exclusive `--spec` + `--theme-from-template`, neither mode supplied (no silent inference), `--theme-from-template` without `--template-root`, `--template-root` supplied without `--theme-from-template`, `--template-root` not a directory, source-body marker phrase NEVER copied into the design_system, mocked post-write rollback (return errors / raise `SystemExit`), on-disk re-validation, and a custom (non-business_review) template name resolved correctly via `--template-root`. After `init_design_system.py` succeeds, Stage 5 (`slide_plans/*.json`) has narrow contract support via `scripts/init_slide_plans.py` (described next); after that helper succeeds, Stage 6 (`image_manifest.json`) has narrow contract support via `scripts/init_image_manifest.py` (caller supplies `--spec`) before `scripts/run_pipeline.py` can take over for stages 7–10.

The Stage-4 → Stage-5 *producer* side has narrow contract support via `scripts/init_slide_plans.py`: given a workspace that already passes the intake bridge AND ships schema-valid `deck_brief.json` + `deck_plan.json` + `design_system.json`, plus a required `--template-root <dir>` (against which `deck_plan.template` must resolve — no product-level default; `business_review` is just the template the current repo ships) and a required `--specs-dir <dir>` of caller-supplied `*.json` slide-plan candidates, the helper iterates the specs at the directory root, refuses any symlink (at `--specs-dir` itself or at an individual spec file), parses each as JSON, validates it against `schemas/slide_plan.schema.json`, and cross-checks coverage against `deck_plan.slides[]`: every spec's `index` must match exactly one deck_plan slide (no duplicates across spec files, no missing slides, no orphan specs), `spec.layout` / `spec.title` must agree with the deck_plan slide's `layout` / `title`, every layout referenced by the deck_plan must be declared by `template.layouts`, and every required slot of the per-layout file under `<template-root>/<deck_plan.template>/layouts/<layout>.json` must be covered by a matching slide_plan block (id + kind, via the shared `_slide_plan_against_layout` gate). The helper re-runs the planner-semantics cross-check `init_deck_plan.py` applies before writing a Stage-3 artifact (re-using `init_deck_plan._cross_check_planner_semantics` — planned-count equality, contiguous 1..N indices, section coverage 1:1, slide.section_id resolution, slide.source_refs subset of deck_brief.source_refs) so a deck_plan `init_deck_plan.py` would not have written is refused before Stage-5 advances. The **pre-D-One local image-asset materialization gate** `scripts/materialize_image_assets.py` is the place to actually place the PNG / JPG / JPEG asset bytes into the workspace paths declared by `image_manifest.json`. Given a workspace that already ships a schema-valid `image_manifest.json` plus a `--assets-dir <dir>` of local PNG / JPG / JPEG files keyed by `<id>.<ext>`, the helper either **copies** the asset bytes into the declared `local_path` targets when the target does not yet exist or **verifies** the pre-existing target in place when it does — in both cases the post-condition is that every declared target is a regular non-symlink file whose first bytes match the declared extension's PNG (`89 50 4E 47 0D 0A 1A 0A`) / JPEG (`FF D8 FF`) magic-byte signature. The verify-or-copy semantics support two distinct workflows; `scripts/init_image_manifest.py` itself refuses to overwrite a pre-existing `image_manifest.json`, so the two workflows do NOT chain through it (each stands on its own, and the manifest must already be in place before materialize runs): **direct-author workflow (no init helper)** — the agent writes `<workspace>/image_manifest.json` directly (e.g. by copying an authored spec JSON verbatim), places PNG / JPG / JPEG asset bytes under `--assets-dir`, then runs materialize; every declared target hits the **copy** branch; `init_image_manifest.py` is NOT invoked in this path (it would refuse to overwrite the already-written manifest); **init_image_manifest workflow (assets pre-placed)** — the agent places asset bytes directly at `<workspace>/<local_path>` for every declared image, then runs `scripts/init_image_manifest.py --workspace ws --spec spec.json` (which requires every declared `local_path` to already resolve to an existing regular non-symlink file before it writes the manifest); materialize is then an OPTIONAL follow-up that takes the **verify-only** branch for every target (defense in depth — `init_image_manifest` only checks file existence at each declared `local_path` and does NOT check PNG / JPEG magic bytes). Re-running on a fully-materialized workspace (whichever workflow produced it) is idempotent. **This is the pre-D-One local asset gate, not D-One itself** — it makes a place for real D-One bytes (or any other local image producer) to plug in upstream, without making any of the safety decisions D-One itself will need a separate policy review for. Fail-closed gates: URI-shaped / symlink `--workspace` / `--assets-dir` refused; `<workspace>/image_manifest.json` must be a regular non-symlink schema-valid file; no duplicate `images[].id`; every `local_path` passes the same path-safety rule the rest of the repo enforces; every declared extension is one of `.png` / `.jpg` / `.jpeg` (SVG / GIF / WebP / TIFF / BMP / ICO refused at the extension gate because the exporter falls back to a placeholder shape for them); leaf-symlink and parent-symlink checks at every target run BEFORE `_resolves_within` so a target symlink pointing outside the workspace surfaces with the clear "symlink" diagnostic; **per-image branch — if the target pre-exists it must be a regular non-symlink file whose first bytes match the magic signature for the declared extension (verify-only path; the corresponding `--assets-dir` file, if any, is left unused); if the target does not exist the source `<assets-dir>/<id>.<ext>` must be a regular non-symlink file whose first bytes match the same signature**; files at the `--assets-dir` root that the manifest does not name refused as undeclared assets (independent of whether the matching target is pre-existing); subdirectories at the root refused (the contract is flat keyed by id+extension); symlink entries at the root refused. Apply / rollback contract: the apply loop iterates only over scheduled copy entries (verify-only entries skip the loop entirely — nothing is written for them, and they are not added to the rollback set); each copied target is added to the rollback set BEFORE its `open('wb')` call so a half-written file at the failing path is still cleaned up; the apply re-checks magic bytes against the FULL payload (TOCTOU defense); a mid-loop OR post-condition failure rolls back every target the helper wrote in this run. Post-condition: `image_manifest.json` bytes byte-identical pre/post (the helper never opens the manifest for writing); every declared target is a regular non-symlink file matching the magic signature. The helper does NOT call D-One / Qoder / any public network / image generation / image search / model API / external service, does NOT open `input/source.md` for business content, does NOT invent prompts, does NOT generate full-slide screenshots, and does NOT produce `render_models/*` / `svg_previews/*` / any `.pptx`. See `references/d-one-image-policy.md` for the policy that any real D-One integration must satisfy before it ships.

The Stage-5 → Stage-6 *producer* side has narrow contract support via `scripts/init_image_manifest.py`: given a workspace that already passes the intake bridge AND ships schema-valid `deck_brief.json` + `deck_plan.json` + `design_system.json` + a non-empty `slide_plans/` directory whose every `*.json` file is a regular file (no symlinks) and validates against `schemas/slide_plan.schema.json`, plus a caller-supplied `--spec` JSON file whose shape is exactly the image_manifest candidate the caller wants written, the helper validates the spec against `schemas/image_manifest.schema.json` (refusing list-rooted JSON, malformed JSON, and symlink specs at the preflight), refuses duplicate `images[].id` values, and runs every `images[].local_path` through the same path-safety stack the workspace validator uses (`validate_scaffold.local_path_is_safe` + within-workspace resolution); the resolved target must additionally be an existing regular file that is not itself a symlink, so an asset symlink (in-workspace or escaping) is refused with a clear "symlink" diagnostic before any cross-check fires. The helper re-runs the planner-semantics cross-check `init_deck_plan.py` applies before writing a Stage-3 artifact (re-using `init_deck_plan._cross_check_planner_semantics`) so a deck_plan `init_deck_plan.py` would not have written is refused before Stage-6 advances; the helper also re-runs the Stage-5 slide-plan coverage gate `init_slide_plans.py` applies — the union of `slide_plan.index` values must exactly cover `deck_plan.slides[].index` (no duplicate indices across slide_plan files, no missing slides, no orphan slide_plans), and each pair's `layout` / `title` must agree with the deck_plan slide, so a hand-edited `slide_plans/` that drifts from `deck_plan` is refused before Stage-6 advances (slot coverage against the per-layout file is NOT re-run here — it needs the template root, and Stage-5 already enforced it on the producer side). Every `slide_plan.image_refs[*]` value across the workspace must be declared in `images[].id`; an empty `images[]` list is accepted ONLY when no slide_plan references any image, and the cross-check surfaces a clear diagnostic on the "empty images + non-empty refs" mismatch. **This is Stage-6 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper itself never opens `input/source.md` (it invokes the Stage-1/Stage-2 bridge, which reads the source bytes only for byte-level integrity checks: UTF-8 decode validity, byte_count / line_count / sha256 match against the manifest, and discards the decoded string), never generates any image asset, never calls D-One / Qoder / any public network / image generation / external service, never produces `render_models/*` / `svg_previews/*` / any `.pptx`, and emits no artifact other than `<workspace>/image_manifest.json`. A pre-existing `image_manifest.json` regular file is refused with prior bytes preserved (no overwrite); a symlink at the output path (broken or resolvable) is refused outright by an explicit symlink preflight that runs BEFORE the regular-file existence check, so a dangling link cannot be followed by `write_text()`. The candidate manifest is schema-validated in memory before any write and re-validated on disk afterwards via `scripts/validate_artifacts.py`; a post-write re-validation failure (return errors OR raise) removes the just-written manifest so the workspace returns to its pre-call state. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s `SystemExit` branch on read-errors still routes through rollback. `--self-test` exercises 28 in-script tempfixture scenarios under `tempfile.TemporaryDirectory()` covering: happy path with one local asset, happy path with empty `images[]` + no `image_refs`, determinism between two independent runs (byte-identical manifest), missing `--spec`, symlink `--spec`, malformed `--spec` (non-JSON), schema-invalid `--spec` (missing required `images`), list-rooted `--spec`, duplicate `images[].id`, three unsafe `local_path` variants (URI / POSIX-absolute / `..` traversal), missing image asset, symlinked image asset, undeclared `slide_plan.image_refs` id, pre-existing `image_manifest.json` refused with prior bytes preserved, broken symlink at `image_manifest.json` (dangling target never created), resolvable symlink at `image_manifest.json` (outside target bytes preserved), empty `slide_plans/` rejected as a Stage-5 prerequisite failure, URI-shaped `--workspace`, source-body marker phrase NEVER copied into the manifest (proves no content extraction), mocked post-write re-validation returning errors (rollback), mocked post-write re-validation raising `SystemExit` (catch clause is `(Exception, SystemExit)`, not bare `Exception`), the "empty images + non-empty refs" cross-check diagnostic, and the Stage-5 coverage gates (missing slide_plan whose index `deck_plan` declares, orphan slide_plan whose index `deck_plan` does not declare, duplicate slide_plan indices across two files, slide_plan/deck_plan title mismatch). After `init_image_manifest.py` succeeds, `scripts/run_pipeline.py` can take over for stages 7–10.

Stage 7 is the only stage between the per-slide plan and the consumers of the controlled model. Its contract is the controlled primitive / layout model defined in `schemas/render_model.schema.json` and described in `references/slide-contracts.md`. Stage 7 is the boundary the SVG renderer (stage 8) and the PPTX exporter (stage 10) **both** consume directly — they do not read `slide_plan.json` and the PPTX exporter does **not** parse the SVG. Stages 8/9 produce the preview / validation artifact; stage 10 produces native PPTX objects from the same render model.

Stage 7 is **partially implemented**: `scripts/generate_render_models.py` produces deterministic render models for every layout reachable from the controlled `text` / `line` / `shape` / `image_slot` / `kpi` / `table` primitive set — `cover`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `kpi_dashboard`, `timeline`, `agenda`, `conclusion`, `comparison_table`. Layouts whose required slot maps to the `chart_placeholder` primitive_kind (anything chart-bearing) are listed as `[SKIP] … not implemented` by the script and are **not** counted as success. Slides for unsupported layouts have no `render_model.json` and cannot proceed to stages 8 / 10 until the generator is extended. Two phrasings to keep distinct: which layouts the **render-model generator can produce end-to-end** from a slide_plan (this stage), and which layouts the **PPTX exporter can consume** (stage 10) — today both sets are the same. The script is fail-closed on missing / malformed inputs, unsafe `deck_plan.template`, unknown `image_ref`, malformed kpi entries, malformed comparison_table headers / rows (wrong column count, empty cell), missing required slide_plan block, list slots with empty / non-string content, schema-invalid output, or workspace cross-check failure.

The render-model output is canonically named `<index:02d>_<layout>.json` (zero-padded two-digit index + layout token from the JSON — e.g. `02_agenda.json`, `09_two_column.json`). The workspace validator's `check_render_model_filenames` gate (`render.filename` in `references/quality-gates.md`) enforces this on disk, because the stage-10 PPTX exporter iterates `deck_plan.slides[]` in declared order and resolves each entry to its canonical render_model filename — a mis-named file would otherwise appear orphan to the exporter (and its canonical counterpart would appear missing), failing the 1:1 coverage gate. This naming rule is render-model-specific. **The slide_plans path layout is committed at both ends**: `scripts/init_slide_plans.py` writes `<workspace>/slide_plans/<idx:02d>_<layout>.json` on the producer side (Stage 5), and the workspace validator's `check_slide_plan_filenames` gate (`slide_plan.filename` in `references/quality-gates.md`) enforces the same canonical shape on disk so hand-edited or migrated workspaces cannot drift — see `references/slide-contracts.md`.

Stages 8 / 9 are **partially implemented**: `scripts/generate_svg_previews.py` reads every render_model the generator emits and writes one `svg_previews/<stem>.svg` per slide. It supports the primitive kinds the render-model generator emits today (`text`, `line`, `shape`, `image_slot`, `kpi`, `table`); every other kind (`chart_placeholder`, future kinds) fails closed on that slide. Validation runs as `check_svg_previews` inside `scripts/validate_workspace.py` — see `references/svg-design-rules.md` and `references/quality-gates.md` for the exact gates. Automatic SVG repair (out-of-bounds clipping, font fallback, density thresholds) remains TODO.

Stage 10 (PPTX export) is **partially implemented**. `scripts/export_pptx.py` is a deterministic, stdlib-only OOXML exporter driven by `deck_plan.json`: it iterates `deck_plan.slides[]` in declared order, resolves each entry to its canonical `render_models/<idx:02d>_<layout>.json`, and emits one PPTX slide per deck_plan entry. It never reads `slide_plan.json`, never `svg_previews/*.svg`, and never any rasterized slide image. A `deck_plan` declaring N slides whose `render_models/` is missing one file (or carries an orphan file) fails closed at the 1:1 coverage gate before any output is written. The expanded native editable subset it currently supports is:

- layouts: `cover`, `kpi_dashboard`, `agenda`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `timeline`, `conclusion`, `comparison_table`. The slide-body emitter is layout-agnostic — it walks each render_model's `primitives` list — so widening the allow-list does not change how any single shape is rendered. Every layout declared by the business_review template skeleton is currently in the allow-list;
- primitive kinds: `text` (editable text frame), `line` (native connector), `shape` (native preset rect / roundRect / ellipse), `kpi` (stacked-paragraph editable text frame), `image_slot` (native `<p:pic>` for PNG / JPG / JPEG manifest entries — bytes copied into `ppt/media/imageN.<ext>` deterministically by manifest order, matching `<Default Extension="..." ContentType="image/png|image/jpeg"/>` registered in `[Content_Types].xml`, per-slide `image` relationship with internal Target `../media/imageN.<ext>` — and a native placeholder rectangle carrying `image_manifest` alt_text for every other extension; SVG / GIF / WebP embedding remains TODO), `table` (native `<p:graphicFrame>` wrapping `<a:tbl>` with one `<a:gridCol>` per column, a bold header row, and an editable `<a:txBody>` per cell).

Everything outside that subset fails closed:

- `chart_placeholder` primitive — per-slide fail with a clear error;
- layouts outside the SUPPORTED_LAYOUTS allow-list above — per-slide fail-closed; the whole run aborts and no `.pptx` is written. Every layout declared by the business_review template skeleton is currently in scope; new layouts must add a paired generator branch before they may appear here. The exporter contract is intentionally all-or-nothing — a workspace containing any out-of-scope render_model fails the run rather than silently dropping that slide;
- wrong `--output` extension (must be `.pptx`), malformed render_model, undeclared `image_ref`, manifest `local_path` with a URI scheme, embeddable PNG / JPG / JPEG manifest entry whose resolved path escapes the workspace OR is a symlink (broken or resolvable) OR is not a regular file OR exceeds the 10 MiB embed cap OR fails the magic-byte check — preflight fail-closed before the ZIP is written.

`scripts/validate_pptx_contract.py` gates the produced `.pptx`:

- with `--pptx <path>` it runs the basic OOXML container checks (file exists, `.pptx` extension, readable ZIP, required package entries `[Content_Types].xml`, `_rels/.rels`, `ppt/presentation.xml`) **plus** a minimal-evidence layer (`slide_count.inspectable`, `relationships.no_external`, `relationships.no_file_uri`, `relationships.allow_list` over `{officeDocument, slide, slideMaster, slideLayout, theme, image}`, `media.targets_internal`, `media.inventory`, `media.embedded_only` (no `<a:blip r:link="…"/>` anywhere in the package's content XML; read + parse handling is fail-closed against `zipfile.BadZipFile` / `RuntimeError` and unparseable XML so a corrupted or malformed in-scope part is recorded as an offender rather than silently passing), `package.no_macros`, `package.no_ole`, `package.no_activex`, `minimal_evidence.editable_text`, `minimal_evidence.not_all_image_slide`, `minimal_evidence.no_blank_slide`, `minimal_evidence.every_slide_has_native_shape`);
- without `--pptx` it runs in skeleton mode and only reports the TODO surface (full-inventory editability, theme palette mapping, determinism, validator-side layout / primitive scope);
- `--self-test` exercises tempfixture negatives for every gate above (missing path, wrong extension, non-zip content, empty ZIP, ZIP missing `ppt/presentation.xml`, external rel, `file://` rel, unexpected relationship `Type`, vbaProject.bin, oleObject.bin, activeX.xml, all-image slide (fails both `not_all_image_slide` and `every_slide_has_native_shape`), no editable text, blank slide alongside an editable one, external image rel, dangling image-rel Target, orphan `ppt/media/` part, `ppt/media/image1.gif` outside the embed allow-list, slide carrying `<a:blip r:link="rIdL"/>` alongside an editable text shape, unparseable XML at `ppt/theme/theme1.xml` (no fail-open parse path), direct unit-test that stub-injected `zipfile.BadZipFile` + `RuntimeError` on read are recorded as `media.embedded_only` offenders (no fail-open read path)) plus positives (minimal valid container, minimal editable PPTX, minimal PNG-embed PPTX whose slide carries `<p:pic>` with `<a:blip r:embed="rId1"/>` next to the editable text shape — so the positive exercises `media.embedded_only`'s accept path — passing `media.targets_internal` + `media.inventory` + `media.embedded_only`).

A passing run of the validator therefore proves the container shape, the absence of macro / OLE / ActiveX parts and external / `file://` relationships, the relationship `Type` allow-list, the embedded-media inventory + targets-internal + embedded-only gates, and minimal evidence of editable native content on every slide. It does NOT prove the full-inventory editability / theme palette / determinism / validator-side scope TODO surface — that work remains.

`scripts/inspect_pptx_inventory.py --pptx <path>` is the **structured readback inventory** that complements the validator's pass/fail lines. It reads the same package and emits a deterministic JSON document (sorted keys / findings / slides / media parts / relationships) with slide count, per-slide native object counts (`shapes_sp` / `connectors_cxnSp` / `pictures_pic` / `graphic_frames` / `tables` / `text_bodies` / `text_runs`), per-slide media refs (rId / Target / resolved part / a `used_by_slide_blip` flag that is True iff a `<a:blip r:embed="rIdN"/>` in the slide actually consumes the rId), embedded media parts under `ppt/media/` (size, sha256, extension, declared content_type, referencing slides), the full relationship list, and `findings[]` for `relationships.external` / `relationships.file_uri` / `relationships.absolute` / `relationships.path_traversal` / `media.missing` / `media.orphan` / `media.unsupported_extension` / `slide.image_only` / `media.linked_blip` (any `<a:blip r:link="..."/>` anywhere in slides / slideMasters / slideLayouts / theme / presentation — same surface `media.embedded_only` refuses) / `package.unreadable_zip` / `package.unreadable_xml`. Exit 0 iff no findings; otherwise exit 1 (JSON still emitted so a CI surface can read what failed). The top-level `evidence_basis` field commits to `"OOXML structure only; not proof of full PowerPoint editability"`. The script is inspection-only — never modifies the package, never writes outside `--out`, never calls any network. `--self-test` covers happy path, deterministic repeated inventory, image-only slide failure, missing media, image rel with NO `Target` attribute (fails closed on `media.missing`), orphan media, external rel, `file://` rel, absolute-path rel, path-traversal rel, bad XML at a slide part, unsupported media extension, linked-blip `<a:blip r:link/>` in slide content, unparseable XML in a non-slide ppt/ part (no fail-open continue), unreadable ZIP, and nonexistent file — 16 scenarios under `tempfile.TemporaryDirectory()`.

## Stage-1-to-6 local orchestration (explicit-input only)

`scripts/prepare_workspace.py` chains the six Stage-1-through-6 contract helpers above (`init_workspace.py` → `init_deck_brief.py` → `init_deck_plan.py` → `init_design_system.py` → `init_slide_plans.py` → `init_image_manifest.py`) in canonical order from explicit caller-supplied inputs into a workspace that `scripts/run_pipeline.py` can later consume. **This is explicit-input orchestration only, not a full prompt/report/Markdown-to-PPTX automation** — every stage's content comes from the caller (CLI flags or JSON spec files); the orchestrator never parses `input/source.md` for business content, never invents `deck_brief` / `deck_plan` / `design_system` / `slide_plans` / `image_manifest` content, never generates any image asset / `render_models/*` / `svg_previews/*` / `.pptx` / pipeline report, never calls D-One / Qoder / any public network / image generation / telemetry / external service, and never modifies files outside `--workspace`. Fail-closed semantics: the first stage that returns a non-zero exit code halts the run; every downstream stage is marked SKIPPED and is NOT invoked, so no half-baked workspace advances into a later stage. Each stage helper owns its own rollback contract — the orchestrator does NOT roll back earlier-stage artifacts when a later stage fails. The Stage-4 mode-selection gate fires up-front: exactly one of `--design-system-spec` / `--theme-from-template` must be supplied. `--self-test` exercises the happy path through Stage 6 with a two-slide `cover` + `key_message` fixture, per-stage failure short-circuit for each of the six stages (every downstream stage is verified SKIPPED), pre-existing unsafe / non-empty workspace refused at Stage 1, the source-body marker phrase appearing in `input/source.md` only, determinism between two independent runs producing byte-identical Stage-1-through-6 artifacts, and an end-to-end check that the prepared workspace passes `scripts/validate_workspace.py` against the `business_review` template (the same gate `scripts/run_pipeline.py` applies up front).

## Composed runner (stages 7 → 10 → validate, prepared workspaces only)

`scripts/run_pipeline.py` chains stages 7 (`generate_render_models.py`), 8 (`generate_svg_previews.py`), 10 (`export_pptx.py`), and the validator above into a single deterministic local command for a workspace that **already** ships `deck_brief.json`, `deck_plan.json`, `slide_plans/*.json`, `design_system.json`, and `image_manifest.json`. (A caller who wants stages 1→10 in one command — explicit source/spec inputs in, validated `.pptx` out — should use `scripts/run_explicit_pipeline.py` (see next section), which composes `prepare_workspace.py` with this runner.) It runs each existing per-stage script as a subprocess — no logic is duplicated — and runs `validate_workspace.py` first as the input gate, then `validate_pptx_contract.py --pptx --expected-slide-count <len(deck_plan.slides)>` after export. When `--report-dir <dir>` is supplied, the runner appends an optional sixth stage `inspect_pptx_inventory.py --pptx <output> --out <report-dir>/inventory.json` that runs only AFTER the `validate_pptx_contract` stage has passed; a non-zero exit from that subprocess (invocation error OR any finding) fails the pipeline closed, and an upstream-stage failure SKIPs the inventory stage along with every other downstream stage. The inventory is evidence only (OOXML structure counts, media / relationship report, and `findings[]`) — NOT proof of full PowerPoint editability (the readback carries the literal `"OOXML structure only; not proof of full PowerPoint editability"` framing string). When `--report-dir` is omitted, the inventory stage is not added to the stage list and no inventory file is produced anywhere. Stale-inventory hygiene: when `--report-dir` is supplied, the runner unlinks any pre-existing regular `<report-dir>/inventory.json` BEFORE the stages start, so a prior successful run's inventory cannot survive a later failing rerun that aborts before the inventory stage — `inventory.json` is either freshly written by the current run (when the inventory stage ran) or absent (when an upstream stage failed). The unlink is intentionally placed AFTER every preflight gate, never before — so a late preflight failure (`--output` is a symlink / a directory, or the output-parent `mkdir` fails) returns rc=2 without invoking `run_pipeline()` AND without destroying the prior good `inventory.json`. The `pipeline_report.{json,txt}` files are always re-written by `_write_reports()` at end of run, so they cannot go stale and need no analogous cleanup. A non-zero exit from any stage aborts the pipeline; downstream stages are skipped rather than silently passing. Workspace mutability is precise: the runner **regenerates** `<workspace>/render_models/*.json` and `<workspace>/svg_previews/*.svg` in place (each generator owns its subdirectory and sweeps stale files before regenerating), while the prepared-input artifacts and any other files under the workspace are read-only; the final `--output` PPTX MUST live OUTSIDE the workspace, and `--report-dir` MUST live outside it too (a stray `.pptx` or report directory under the workspace tree would otherwise be picked up by `validate_workspace` on a later run). When `--report-dir` is supplied, the runner applies the same shape of pre-existing-path gate it does to `--output`: a symlink at `--report-dir` is refused (consistent with `--output`'s symlink rule — symlinks are never silently followed), a regular file at `--report-dir` is refused (otherwise the pipeline would validate / generate / export to completion and only then crash inside `_write_reports()` with a `FileExistsError`), the directory is pre-created with `mkdir(parents=True, exist_ok=True)` up-front, and writability is then probed by opening + closing + deleting a `NamedTemporaryFile` inside the directory — because `mkdir(exist_ok=True)` succeeds on an existing read-only directory (the runner does not own / read-only mount / ACL block / full filesystem) without proving the runner can actually write into it, the probe is what closes the gate. The directory probe alone is still insufficient: `_write_reports()` writes two specific filenames (`pipeline_report.json` / `pipeline_report.txt`) via `Path.write_text()`, which follows symlinks and fails on directories or read-only regular files, so the runner ALSO refuses, before any stage runs, a pre-existing symlink at either report-file path (would silently redirect the write to an unrelated target), a non-regular-file at either path (a directory would raise `IsADirectoryError`), and an existing regular file at either path that lacks user write permission (`os.access(..., os.W_OK)` is False; `write_text` would raise `PermissionError`). Any unrelated permission / parent-not-a-directory / read-only-filesystem / full-disk error therefore surfaces BEFORE any stage runs rather than after the PPTX has already been written. With `--report-dir <dir>` the runner writes `pipeline_report.json` (machine-readable), `pipeline_report.txt` (human-readable summary), AND `inventory.json` (the deterministic OOXML structure readback from `inspect_pptx_inventory.py`; sorted-keys / findings / slides / media_parts / relationships; `evidence_basis = "OOXML structure only; not proof of full PowerPoint editability"`) — all three refused when `<dir>` resolves inside the workspace, points at a symlink, already exists as a non-directory, exists as a directory that fails the writability probe, or contains a pre-existing `pipeline_report.{json,txt}` or `inventory.json` that is a symlink, a non-regular-file, or a read-only regular file. `--self-test` builds tempfile-based synthetic workspaces (copied from `examples/synthetic_8_page_product_brief/`) and exercises twenty-one scenarios end-to-end: happy path, wrong `--output` extension, `--output` inside the workspace, `--report-dir` inside the workspace, pre-existing regular file at `--report-dir` (refused before any stage runs, no PPTX written, prior file preserved byte-identical), pre-existing symlink at `--report-dir` (refused, symlink's target directory untouched and no `pipeline_report.{json,txt}` written into it), pre-existing read-only directory at `--report-dir` (writability probe; refused before any stage runs; auto-skipped under root because `chmod` cannot meaningfully restrict root), pre-existing symlink at `<report-dir>/pipeline_report.json` (refused; unrelated symlink target preserved byte-identical; no PPTX written), pre-existing read-only `<report-dir>/pipeline_report.txt` (refused; prior content preserved byte-identical; auto-skipped under root), happy-path `--report-dir` outside the workspace writes `pipeline_report.json` + `pipeline_report.txt` with `overall_ok=true`, happy-path `--report-dir` writes `inventory.json` with `ok=true` and the `evidence_basis` framing line, happy path WITHOUT `--report-dir` produces no `inventory.json` and does not add the inventory stage, pre-existing symlink at `<report-dir>/inventory.json` refused before any stage runs (unrelated target preserved byte-identical), `validate_workspace` failure with `--report-dir` cascading `[SKIP]` to `inspect_pptx_inventory` too (no `inventory.json` created), stale `inventory.json` from a prior successful `--report-dir` run is removed BEFORE a later failing rerun's stages execute (so the caller never sees a fresh FAIL `pipeline_report` next to a stale `inventory.json` from a different run), a LATE preflight failure (`--output` is a symlink) with the same `--report-dir` preserves the prior `inventory.json` byte-identical (the destructive unlink only runs AFTER every preflight gate), `--output` parent path blocked by a regular file returns rc=2 with a clean FAIL diagnostic (no Python traceback) and the blocker file AND any prior `inventory.json` are preserved byte-identical, pre-existing symlink at `--output`, pre-existing directory named `*.pptx` at `--output`, `validate_workspace` failure cascading `[SKIP]` across every downstream stage, and a prior regular `.pptx` preserved byte-identical when `validate_workspace` fails before export. Stage 1 (Intake) is now automated by `scripts/init_workspace.py`: it seeds a brand-new workspace from a single local `.md` / `.txt` source by writing `<workspace>/input/source.md` + `<workspace>/source_manifest.json` (schema-backed against `schemas/source_manifest.schema.json`). Stage 2 (Brief) has **narrow contract support** via `scripts/init_deck_brief.py`: from a stage-1 workspace plus explicit `--title` / `--audience` / `--objective` (and optional `--tone` / `--language` / `--approximate-slide-count`), the helper writes a minimal schema-valid `deck_brief.json` whose `source_refs` carries `source_manifest.source.id` — without extracting any business content from the source body, so it is NOT a full prompt/report-to-PPTX automation. Stage 3 (Plan) has **narrow contract support** via `scripts/init_deck_plan.py`: from a stage-2 workspace plus a `--plan-spec` JSON file describing the plan content, the helper validates the spec against `schemas/deck_plan.schema.json` and the planner-semantics cross-checks (planned-count equality, unique + contiguous slide indices, section coverage, slide.section_id resolution, slide.source_refs subset of deck_brief.source_refs) and writes `<workspace>/deck_plan.json` — without extracting any business content from the source body, so it is also NOT a full prompt/report-to-PPTX automation. Stage 4 (Design system) has **narrow contract support** via `scripts/init_design_system.py`: from a stage-3 workspace plus EXACTLY ONE explicit caller input (`--spec <design_system.json>` OR `--theme-from-template` + `--template-root <dir>`), the helper validates the candidate against `schemas/design_system.schema.json` and writes `<workspace>/design_system.json`; template resolution is anchored on `deck_plan.template` (no product-level default), and the helper never infers design from raw source text, so it is also NOT a full prompt/report-to-PPTX automation. Stage 5 (Per-slide Plans) has **narrow contract support** via `scripts/init_slide_plans.py`: from a stage-4 workspace plus a required `--template-root <dir>` (no product-level default) and a required `--specs-dir <dir>` of caller-supplied `*.json` slide-plan candidates, the helper validates every candidate against `schemas/slide_plan.schema.json`, cross-checks 1:1 coverage against `deck_plan.slides[]` (no missing / orphan / duplicate slides, layout/title match, every required layout slot covered, deck_plan layouts declared by the template), and writes `<workspace>/slide_plans/<idx:02d>_<layout>.json` — without extracting any business content from the source body, so it is also NOT a full prompt/report-to-PPTX automation. Stage 6 (Image manifest) has **narrow contract support** via `scripts/init_image_manifest.py`: from a stage-5 workspace plus a caller-supplied `--spec` JSON file whose shape is exactly the image_manifest candidate, the helper validates the spec against `schemas/image_manifest.schema.json`, refuses duplicate `images[].id` and unsafe `local_path`, requires every `local_path` to resolve inside the workspace to a regular non-symlink file, and cross-checks every `slide_plan.image_refs[*]` against `images[].id` — without generating any image asset, calling D-One / Qoder / any public network, or extracting source content, so it is also NOT a full prompt/report-to-PPTX automation. The runner refuses any workspace whose stage-3-through-6 artifacts are missing or malformed via its first stage (`validate_workspace.py`).

## Stage-1-to-10 end-to-end orchestration (explicit-input only)

`scripts/run_explicit_pipeline.py` chains the Stage-1-to-6 explicit-input orchestrator (`scripts/prepare_workspace.py`, invoked in-process so the structured per-stage result is preserved for reporting) and the Stage-7-to-10 prepared-workspace pipeline (`scripts/run_pipeline.py`, invoked as a subprocess so its existing fail-closed gates, `[PASS]/[SKIP]/[FAIL]` cascade, and optional `--report-dir` writes are reused verbatim — no stage logic is duplicated) into one local, deterministic command that produces a validated editable PPTX from caller-supplied source/spec files. **This is explicit-input end-to-end orchestration only, not a full prompt/report/Markdown-to-PPTX automation** — every Stage-1-to-6 artifact's content comes from the caller (CLI flags or JSON spec files); Stage 7-10 consumes only what Stage 1-6 wrote; the orchestrator never parses `input/source.md` for business content, never invents `deck_brief` / `deck_plan` / `design_system` / `slide_plans` / `image_manifest` content, never generates any image asset / spec / slide body, never calls D-One / Qoder / any public network / image generation / telemetry / external service, never duplicates per-stage logic, and never modifies files outside `--workspace` apart from the final `--output` PPTX and (if supplied) `--report-dir`. Fail-closed semantics: if Stage-1-to-6 preparation fails at any stage (non-zero exit), the Stage-7-to-10 pipeline is NOT invoked at all — no `render_models/`, `svg_previews/`, `.pptx`, or `pipeline_report.{json,txt}` is produced; if Stage-7-to-10 fails, the failing stage is reported clearly via the pipeline subprocess's own `[FAIL] <stage>` / `[SKIP] <stage>` cascade plus stderr tail. The orchestrator owns three up-front gates only — required-args check, the Stage-4 mode-selection gate (`--design-system-spec` XOR `--theme-from-template`), and the `--output` extension check (`.pptx`) — to fail fast on obvious user errors before a six-stage prep run is wasted; every other `--output` / `--report-dir` safety gate (inside-workspace, symlink, non-regular-file, pre-existing report-file paths) is delegated to `scripts/run_pipeline.py` for defense in depth. `--self-test` exercises tempfixture scenarios under `tempfile.TemporaryDirectory()` covering: the happy path (explicit source/spec inputs produce a validated PPTX with every Stage-1-to-6 stage PASS and every Stage-7-to-10 stage PASS), preparation failure short-circuiting the pipeline (empty source → init_workspace fails → no render_models / svg_previews / PPTX produced, every downstream prep stage SKIP, pipeline never invoked), pipeline failure reported clearly (a pre-existing directory at `--output` is caught by `run_pipeline`'s gate after prep succeeds; the orchestrator surfaces the diagnostic and the directory's canary file is untouched), wrong `--output` extension failing fast in the orchestrator before any prep stage runs (no workspace is created), `--output` inside the workspace refused by `run_pipeline`'s delegated gate (no `.pptx` written inside the workspace tree), the source-body marker phrase never copied into any artifact beyond `<workspace>/input/source.md` (source_manifest / deck_brief / deck_plan / design_system / slide_plans / image_manifest / render_models / svg_previews / the PPTX bytes are all checked), and deterministic repeated runs from byte-identical inputs both passing validation with byte-identical Stage-1-through-6 artifacts across the two runs.

## MVP acceptance smoke (synthetic authoring trial)

`scripts/acceptance_smoke.py` is the narrow end-to-end acceptance gate for the implemented explicit-input pipeline. It composes the existing scripts — `validate_authoring_bundle.py` (preflight) → `run_explicit_pipeline.py` with `--report-dir` (Stage 1-to-10 orchestration; internally runs `validate_workspace`, `generate_render_models`, `generate_svg_previews`, `export_pptx`, `validate_pptx_contract`, and `inspect_pptx_inventory`) → `validate_pptx_contract.py --pptx ... --expected-slide-count N` (belt-and-braces direct re-validation with the slide-count gate active) → `validate_visual_quality.py --workspace ... --output <report-dir>/visual_quality.json` (post-pipeline visual review; the deterministic JSON report is persisted alongside the pipeline reports so the smoke leaves a reviewable artifact, not just stdout) — against the synthetic authoring trial bundle (`examples/synthetic_authoring_trial/`) into a temporary output directory that lives OUTSIDE the committed example tree. Fail-closed: any stage exiting non-zero, or any post-condition failing, aborts the smoke immediately. The smoke refuses an `--output-root` that resolves inside a refused top-level directory under the repo (`examples/`, `references/`, `schemas/`, `scripts/`, `templates/` — these ship committed source bytes; **`.git/`** — git metadata, writing into it can corrupt the object database / refs / hooks / index; **`.claude/`** — the user's Claude Code project state, writing into it can clobber transcripts / memory / hook config) or equals the repo root itself, so generated PPTX / reports / render_models / SVG never land in the committed tree, git metadata, or the harness's session state. ## Adaptive planning

The Brief and Plan stages are **adaptive**, not template-driven:

- The Brief stage derives `deck_brief.json` from the user's request and the normalized source. It captures intent, audience, objective, and any explicit constraints (including `approximate_slide_count` if the caller supplied one). `source_refs` is required and non-empty: every brief lists the opaque source identifiers the deck draws from.
- The Plan stage chooses, for that specific brief: **target slide count**, **section structure**, **which layouts each slide uses**, and **per-slide density**. There is no universal sequence — agenda, section dividers, KPI dashboards, timelines, and conclusion slides are tools the planner *may* use, not slots it *must* fill.
- Expected capacity range is **12–25 slides** as guidance; a real run may produce 6, 8, 10, 15, 20, 25, or another reasonable count. The number depends on the brief, not on the template.
- Different scenarios produce different shapes — e.g. executive summary, product proposal, technical solution, project review, research report, training deck, strategy memo. Template families exist to provide the layout vocabulary; they do not dictate slide count or order.

### Planner contract (machine-enforced)

`deck_plan.json` carries a stricter planner contract that the validators cross-check, while still imposing **no** maximum slide count or required layout sequence:

- `deck_plan.planning.planned_slide_count` must equal `len(deck_plan.slides)`.
- `deck_plan.planning.rationale` is a required short string explaining the planner's length / structure choice.
- `deck_plan.sections[]` (`id`, `title`, `summary`, `slide_indices`) partitions the deck: the union of every section's `slide_indices` must equal the set of `slides[].index` values — no duplicates across sections, no missing deck indices, no orphan section indices.
- Each `slides[]` entry carries `section_id` (must exist; the slide's index must be listed by that section), `summary`, `density` (`low` / `medium` / `high`), and a non-empty `source_refs` whose values must all be declared in `deck_brief.source_refs`.

See `references/slide-contracts.md` and the schemas under `schemas/` for the authoritative shape; `references/quality-gates.md` lists the matching gates.

## Invariants

- Stage `n` may not start until stage `n-1` has produced its output and that output has passed schema validation.
- `deck_plan` must exist before any render-model or SVG work. Per-slide plans must exist before that slide's render model. A slide's render model must exist before that slide's SVG and before its PPTX shapes are emitted.
- The render model is the **only** input to the SVG renderer and the PPTX exporter — neither stage may read `slide_plan.json` directly, so the controlled primitive contract cannot be bypassed.
- SVG is a required **preview / inspection artifact and validation gate** for every slide, not the source language for PPTX. The PPTX exporter does **not** parse SVG; it builds native PowerPoint objects from the same `render_model.json` the SVG renderer consumed. This repo is intentionally not a broad SVG → PPTX converter.
- The terminal output is an **editable** PPTX.

## Project workspace

Each run uses a workspace directory chosen by the caller. All intermediate artifacts live there. The skill must not hardcode `projects/<name>`; the path is always passed in.

## Agent authoring workflow (Stage 2-6 spec creation)

The implemented explicit-input runtime pipeline — the six Stage-2-to-6 contract helpers (`init_deck_brief.py`, `init_deck_plan.py`, `init_design_system.py`, `init_slide_plans.py`, `init_image_manifest.py`) plus the Stage-1 seed `init_workspace.py`, the Stage-1-to-6 orchestrator `scripts/prepare_workspace.py`, the Stage-7-to-10 runner `scripts/run_pipeline.py`, and the Stage-1-to-10 end-to-end orchestrator `scripts/run_explicit_pipeline.py` — is intentionally **explicit-input**: it validates and writes spec files the caller already authored, it does not extract business content from `input/source.md`, and it makes no model API call. The work of reading the source plus the user's request and **authoring** those spec files is the agent's responsibility and lives outside the runtime pipeline. The contract for that agent-side work — what to author, how to keep source fidelity, how to handle images safely, and which checks to run before invoking the runtime pipeline — lives in [`references/authoring-workflow.md`](authoring-workflow.md), kept as a separate document so the authoring workflow is never read as runtime code. Treat the runtime pipeline as the validator + renderer + exporter of the agent's authored specs; do **not** read it as evidence that an automatic prompt-to-PPTX stack, D-One image generation, Qoder runtime packaging, or any model API call exists in this repo — none of those are implemented.
