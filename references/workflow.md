# Workflow

The skill is a single linear pipeline. Stages are append-only; do not skip or reorder.

| # | Stage | Input | Output | Schema |
|---|---|---|---|---|
| 1 | Intake | local Markdown / text source file (`--source`) | `<workspace>/input/source.md` + `<workspace>/source_manifest.json` (written by `scripts/init_workspace.py`; this script does NOT plan a deck and does NOT generate any later-stage artifact) | `schemas/source_manifest.schema.json` |
| 2 | Brief | normalized source | `deck_brief.json` (Stage-2 contract helper `scripts/init_deck_brief.py` writes only the schema-required skeleton — `title`/`audience`/`objective` from explicit `--title`/`--audience`/`--objective` flags plus `source_refs = [source_manifest.source.id]` — and never extracts business content from `input/source.md`; it does NOT plan a deck) | `schemas/deck_brief.schema.json` |
| 3 | Plan | `deck_brief.json` | `deck_plan.json` (adaptive length, structure, layouts, density; Stage-3 contract helper `scripts/init_deck_plan.py` validates a caller-supplied `--plan-spec` JSON file against the schema + planner-semantics cross-checks and writes the result — it does NOT extract business content from `input/source.md` and is NOT a full prompt/report-to-PPTX automation) | `schemas/deck_plan.schema.json` |
| 4 | Design system | `deck_plan.json` + template | `design_system.json` | `schemas/design_system.schema.json` |
| 5 | Per-slide plan | `deck_plan.json` + `design_system.json` | one `slide_plan.json` per slide | `schemas/slide_plan.schema.json` |
| 6 | Image manifest | per-slide plans | `image_manifest.json` | `schemas/image_manifest.schema.json` |
| 7 | Render model | per-slide plan + design_system + image_manifest + layout slots | one `render_model.json` per slide (controlled primitives, bounds, token-only style refs) | `schemas/render_model.schema.json` |
| 8 | SVG render | per-slide render model | one SVG preview per slide under `svg_previews/` (partial: `text`, `line`, `shape`, `image_slot`, `kpi`, `table`) | XML; controlled by `check_svg_previews` in `scripts/validate_workspace.py` |
| 9 | SVG validate | per-slide SVG | pass/fail against `check_svg_previews` | implemented (repair: TODO) |
| 10 | PPTX export | per-slide render model | one editable PPTX (native shapes / text frames / connectors / tables) | partially implemented — `scripts/export_pptx.py` exports the supported subset (layouts `cover`, `kpi_dashboard`, `agenda`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `timeline`, `conclusion`, `comparison_table`; primitives `text` / `line` / `shape` / `image_slot` / `kpi` / `table`); `scripts/validate_pptx_contract.py --pptx` runs the container + minimal-evidence safety/editability gates against the result (including `relationships.allow_list` and `minimal_evidence.every_slide_has_native_shape`); everything outside that scope still fails closed |
| 11 | Reports | PPTX + artifacts | security / editability / visual reports | TODO |

Stage 1 → 2 is gated by an **intake bridge** the validators apply when a workspace ships `source_manifest.json` as a **regular in-workspace file** — a symlink at that path (broken or resolvable) is refused outright by a symlink preflight that runs BEFORE `_try_load` / `read_text`, so neither a dangling link masquerading as the legacy "no manifest" no-op nor a resolvable link reading manifest bytes from outside the workspace can slip through. `scripts/validate_workspace.py` and `scripts/validate_scaffold.py` each invoke `check_source_manifest_bridge` (see `source_manifest.bridge` in `references/quality-gates.md`) which applies the symlink preflight first, then schema-validates the manifest, confirms `source.local_path == "input/source.md"` resolves inside the workspace and exists as a regular UTF-8 file whose `byte_count` / `line_count` / `sha256` match the on-disk source, and confirms `source.kind` is one of the schema-documented values (`markdown` for a .md-original source, `text` for a .txt-original source — `init_workspace.py` normalizes the on-disk filename to `input/source.md` regardless of the original extension, so both kinds are legitimate against the canonical filename). When `deck_brief.json` is present, `deck_brief.source_refs` must declare `source_manifest.source.id`. A Stage-1-only workspace (manifest + source.md, no `deck_brief.json`) is valid by design: the bridge passes every on-disk row and skips the deck_brief cross-check row rather than emitting a FAIL. Workspaces without `source_manifest.json` are a no-op so prepared examples that pre-date `init_workspace.py` remain valid. The bridge is verification-only — it does NOT plan a deck, mutate the workspace, or run any prompt-to-deck automation.

The Stage-1 → Stage-2 *producer* side is automated, narrowly, by `scripts/init_deck_brief.py`: given a workspace that already passes the intake bridge (Stage 1 complete) plus explicit `--title` / `--audience` / `--objective` flags, the helper writes a minimal, schema-valid `deck_brief.json` whose `source_refs` is exactly `[source_manifest.source.id]`. **This is Stage-2 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper does not extract business content from `input/source.md`, does not invent `key_messages` / `constraints` / `tone` / `language` / `approximate_slide_count` when the caller does not pass them, does not plan a deck, and emits no artifact other than `deck_brief.json`. The brief is schema-validated in memory before any write and re-validated on disk afterwards; a post-write re-validation failure rolls the brief back. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s SystemExit branch on read-errors still routes through rollback. `--self-test` exercises 29 in-script tempfixture scenarios under `tempfile.TemporaryDirectory()`, including the symlink preflight at `source_manifest.json` for both a broken and a resolvable link (proving `read_text` / the bridge cannot follow either to read manifest bytes from outside the workspace, and that no `deck_brief.json` is written when either case is detected), the symlink-first guard at `deck_brief.json` for both a broken and a resolvable link (proving `write_text()` cannot follow either and clobber an unrelated target), a marker-phrase test that proves the source body is never copied into the brief, and a mutated-brief test that proves the bridge catches a `source_refs` that drops `source.id`. Stages 3–6 (`deck_plan.json`, `design_system.json`, `slide_plans/*.json`, `image_manifest.json`) remain agent-driven — Stage 3 has the narrow contract helper described next; stages 4–6 are not yet automated.

The Stage-2 → Stage-3 *producer* side now has narrow contract support via `scripts/init_deck_plan.py`: given a workspace that already passes the intake bridge AND ships a schema-valid `deck_brief.json`, plus a `--plan-spec` JSON file whose shape is exactly the deck_plan candidate the caller wants written, the helper validates that spec against `schemas/deck_plan.schema.json` and the planner-semantics cross-checks (`planning.planned_slide_count == len(slides)`, slide indices unique + contiguous 1..N, section coverage 1:1 with deck_plan slides, every `slide.section_id` resolves to a declared section, every `slide.source_refs` value is declared in `deck_brief.source_refs`) and writes the result deterministically to `<workspace>/deck_plan.json`. **This is Stage-3 contract support only, not full prompt/report/Markdown-to-PPTX automation** — the helper does not read or parse `input/source.md`, does not invent `template` / `rationale` / `slides` / `sections` content when the caller does not pass them, does not plan a deck, and emits no artifact other than `deck_plan.json`. Source-id traceability is **deck-level, not per-slide**: the bridge gate guarantees `source_manifest.source.id` is in `deck_brief.source_refs`, and the helper gate guarantees every `slide.source_refs` value is in `deck_brief.source_refs`, so the manifest's source id is part of the deck-bundle every slide draws from. It does NOT follow that every individual slide cites `source_manifest.source.id` — when `deck_brief.source_refs` declares multiple ids, a slide may pick a non-manifest id from that set. The plan is schema-validated in memory before any write and re-validated on disk afterwards; a post-write re-validation failure rolls the plan back. The catch clause is explicitly `(Exception, SystemExit)` so `validate_artifact`'s SystemExit branch on read-errors still routes through rollback. `--self-test` exercises 29 in-script tempfixture scenarios under `tempfile.TemporaryDirectory()`, including the positive happy paths (1-slide / 3-slide), determinism between two independent runs, missing `deck_brief.json` (no silent fallback), malformed deck_brief, a deck_brief whose `source_refs` omits `source_manifest.source.id` (refused at the bridge), `planned_slide_count` mismatch, duplicate slide indices, **non-contiguous slide indices** ([1, 2, 4]), section coverage that omits a slide, section coverage that lists an orphan slide_index, an unknown `slide.section_id`, a `slide.source_refs` value not declared in `deck_brief.source_refs`, the no-source_manifest legacy workspace (refused — the existing prepared examples that pre-date `init_workspace.py` simply do not run this helper), a pre-existing regular-file `deck_plan.json` (refused with prior bytes preserved), broken / resolvable symlink at `deck_plan.json`, broken symlink at `source_manifest.json`, a `--plan-spec` that is a symlink / malformed JSON / list-rooted / schema-invalid, missing / regular-file / URI-shaped `--workspace`, a marker-phrase test that proves the source body is never copied into the plan, and mocked post-write rollback (return errors / raise `SystemExit`). After `init_deck_plan.py` succeeds, stages 4–6 (`design_system.json`, `slide_plans/*.json`, `image_manifest.json`) remain agent-driven before `scripts/run_pipeline.py` can take over for stages 7–10.

Stage 7 is the only stage between the per-slide plan and the consumers of the controlled model. Its contract is the controlled primitive / layout model defined in `schemas/render_model.schema.json` and described in `references/slide-contracts.md`. Stage 7 is the boundary the SVG renderer (stage 8) and the PPTX exporter (stage 10) **both** consume directly — they do not read `slide_plan.json` and the PPTX exporter does **not** parse the SVG. Stages 8/9 produce the preview / validation artifact; stage 10 produces native PPTX objects from the same render model.

Stage 7 is **partially implemented**: `scripts/generate_render_models.py` produces deterministic render models for every layout reachable from the controlled `text` / `line` / `shape` / `image_slot` / `kpi` / `table` primitive set — `cover`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `kpi_dashboard`, `timeline`, `agenda`, `conclusion`, `comparison_table`. Layouts whose required slot maps to the `chart_placeholder` primitive_kind (anything chart-bearing) are listed as `[SKIP] … not implemented` by the script and are **not** counted as success. Slides for unsupported layouts have no `render_model.json` and cannot proceed to stages 8 / 10 until the generator is extended. Two phrasings to keep distinct: which layouts the **render-model generator can produce end-to-end** from a slide_plan (this stage), and which layouts the **PPTX exporter can consume** (stage 10) — today both sets are the same. The script is fail-closed on missing / malformed inputs, unsafe `deck_plan.template`, unknown `image_ref`, malformed kpi entries, malformed comparison_table headers / rows (wrong column count, empty cell), missing required slide_plan block, list slots with empty / non-string content, schema-invalid output, or workspace cross-check failure.

The render-model output is canonically named `<index:02d>_<layout>.json` (zero-padded two-digit index + layout token from the JSON — e.g. `02_agenda.json`, `09_two_column.json`). The workspace validator's `check_render_model_filenames` gate (`render.filename` in `references/quality-gates.md`) enforces this on disk, because the stage-10 PPTX exporter iterates `deck_plan.slides[]` in declared order and resolves each entry to its canonical render_model filename — a mis-named file would otherwise appear orphan to the exporter (and its canonical counterpart would appear missing), failing the 1:1 coverage gate. This naming rule is render-model-specific; the broader workspace path layout for `slide_plans/` and friends remains TODO (see `references/slide-contracts.md`).

Stages 8 / 9 are **partially implemented**: `scripts/generate_svg_previews.py` reads every render_model the generator emits and writes one `svg_previews/<stem>.svg` per slide. It supports the primitive kinds the render-model generator emits today (`text`, `line`, `shape`, `image_slot`, `kpi`, `table`); every other kind (`chart_placeholder`, future kinds) fails closed on that slide. Validation runs as `check_svg_previews` inside `scripts/validate_workspace.py` — see `references/svg-design-rules.md` and `references/quality-gates.md` for the exact gates. Automatic SVG repair (out-of-bounds clipping, font fallback, density thresholds) remains TODO.

Stage 10 (PPTX export) is **partially implemented**. `scripts/export_pptx.py` is a deterministic, stdlib-only OOXML exporter driven by `deck_plan.json`: it iterates `deck_plan.slides[]` in declared order, resolves each entry to its canonical `render_models/<idx:02d>_<layout>.json`, and emits one PPTX slide per deck_plan entry. It never reads `slide_plan.json`, never `svg_previews/*.svg`, and never any rasterized slide image. A `deck_plan` declaring N slides whose `render_models/` is missing one file (or carries an orphan file) fails closed at the 1:1 coverage gate before any output is written. The expanded native editable subset it currently supports is:

- layouts: `cover`, `kpi_dashboard`, `agenda`, `section_divider`, `executive_summary`, `key_message`, `two_column`, `timeline`, `conclusion`, `comparison_table`. The slide-body emitter is layout-agnostic — it walks each render_model's `primitives` list — so widening the allow-list does not change how any single shape is rendered. Every layout declared by the business_review template skeleton is currently in the allow-list;
- primitive kinds: `text` (editable text frame), `line` (native connector), `shape` (native preset rect / roundRect / ellipse), `kpi` (stacked-paragraph editable text frame), `image_slot` (native placeholder rectangle carrying `image_manifest` alt_text — media embedding is intentionally TODO), `table` (native `<p:graphicFrame>` wrapping `<a:tbl>` with one `<a:gridCol>` per column, a bold header row, and an editable `<a:txBody>` per cell).

Everything outside that subset fails closed:

- `chart_placeholder` primitive — per-slide fail with a clear error;
- layouts outside the SUPPORTED_LAYOUTS allow-list above — per-slide fail-closed; the whole run aborts and no `.pptx` is written. Every layout declared by the business_review template skeleton is currently in scope; new layouts must add a paired generator branch before they may appear here. The exporter contract is intentionally all-or-nothing — a workspace containing any out-of-scope render_model fails the run rather than silently dropping that slide;
- wrong `--output` extension (must be `.pptx`), malformed render_model, undeclared `image_ref`, manifest `local_path` with a URI scheme — preflight fail-closed before the ZIP is written.

`scripts/validate_pptx_contract.py` gates the produced `.pptx`:

- with `--pptx <path>` it runs the basic OOXML container checks (file exists, `.pptx` extension, readable ZIP, required package entries `[Content_Types].xml`, `_rels/.rels`, `ppt/presentation.xml`) **plus** a minimal-evidence layer (`slide_count.inspectable`, `relationships.no_external`, `relationships.no_file_uri`, `relationships.allow_list`, `package.no_macros`, `package.no_ole`, `package.no_activex`, `minimal_evidence.editable_text`, `minimal_evidence.not_all_image_slide`, `minimal_evidence.no_blank_slide`, `minimal_evidence.every_slide_has_native_shape`);
- without `--pptx` it runs in skeleton mode and only reports the TODO surface (full-inventory editability, embedded-only media, media inventory, theme palette mapping, determinism, validator-side layout / primitive scope);
- `--self-test` exercises tempfixture negatives for every gate above (missing path, wrong extension, non-zip content, empty ZIP, ZIP missing `ppt/presentation.xml`, external rel, `file://` rel, unexpected relationship `Type`, vbaProject.bin, oleObject.bin, activeX.xml, all-image slide (fails both `not_all_image_slide` and `every_slide_has_native_shape`), no editable text, blank slide alongside an editable one) plus two positives (minimal valid container, minimal editable PPTX).

A passing run of the validator therefore proves the container shape, the absence of macro / OLE / ActiveX parts and external / `file://` relationships, the relationship `Type` allow-list, and minimal evidence of editable native content on every slide. It does NOT prove the full-inventory editability / media inventory / theme palette / determinism / validator-side scope TODO surface — that work remains.

## Composed runner (stages 7 → 10 → validate, prepared workspaces only)

`scripts/run_pipeline.py` chains stages 7 (`generate_render_models.py`), 8 (`generate_svg_previews.py`), 10 (`export_pptx.py`), and the validator above into a single deterministic local command for a workspace that **already** ships `deck_brief.json`, `deck_plan.json`, `slide_plans/*.json`, `design_system.json`, and `image_manifest.json`. It runs each existing per-stage script as a subprocess — no logic is duplicated — and runs `validate_workspace.py` first as the input gate, then `validate_pptx_contract.py --pptx --expected-slide-count <len(deck_plan.slides)>` after export. A non-zero exit from any stage aborts the pipeline; downstream stages are skipped rather than silently passing. Workspace mutability is precise: the runner **regenerates** `<workspace>/render_models/*.json` and `<workspace>/svg_previews/*.svg` in place (each generator owns its subdirectory and sweeps stale files before regenerating), while the prepared-input artifacts and any other files under the workspace are read-only; the final `--output` PPTX MUST live OUTSIDE the workspace, and `--report-dir` MUST live outside it too (a stray `.pptx` or report directory under the workspace tree would otherwise be picked up by `validate_workspace` on a later run). When `--report-dir` is supplied, the runner applies the same shape of pre-existing-path gate it does to `--output`: a symlink at `--report-dir` is refused (consistent with `--output`'s symlink rule — symlinks are never silently followed), a regular file at `--report-dir` is refused (otherwise the pipeline would validate / generate / export to completion and only then crash inside `_write_reports()` with a `FileExistsError`), the directory is pre-created with `mkdir(parents=True, exist_ok=True)` up-front, and writability is then probed by opening + closing + deleting a `NamedTemporaryFile` inside the directory — because `mkdir(exist_ok=True)` succeeds on an existing read-only directory (the runner does not own / read-only mount / ACL block / full filesystem) without proving the runner can actually write into it, the probe is what closes the gate. The directory probe alone is still insufficient: `_write_reports()` writes two specific filenames (`pipeline_report.json` / `pipeline_report.txt`) via `Path.write_text()`, which follows symlinks and fails on directories or read-only regular files, so the runner ALSO refuses, before any stage runs, a pre-existing symlink at either report-file path (would silently redirect the write to an unrelated target), a non-regular-file at either path (a directory would raise `IsADirectoryError`), and an existing regular file at either path that lacks user write permission (`os.access(..., os.W_OK)` is False; `write_text` would raise `PermissionError`). Any unrelated permission / parent-not-a-directory / read-only-filesystem / full-disk error therefore surfaces BEFORE any stage runs rather than after the PPTX has already been written. With `--report-dir <dir>` the runner writes `pipeline_report.json` (machine-readable) and `pipeline_report.txt` (human-readable summary) — both refused when `<dir>` resolves inside the workspace, points at a symlink, already exists as a non-directory, exists as a directory that fails the writability probe, or contains a pre-existing `pipeline_report.{json,txt}` that is a symlink, a non-regular-file, or a read-only regular file. `--self-test` builds tempfile-based synthetic workspaces (copied from `examples/synthetic_8_page_product_brief/`) and exercises fourteen scenarios end-to-end: happy path, wrong `--output` extension, `--output` inside the workspace, `--report-dir` inside the workspace, pre-existing regular file at `--report-dir` (refused before any stage runs, no PPTX written, prior file preserved byte-identical), pre-existing symlink at `--report-dir` (refused, symlink's target directory untouched and no `pipeline_report.{json,txt}` written into it), pre-existing read-only directory at `--report-dir` (writability probe; refused before any stage runs; auto-skipped under root because `chmod` cannot meaningfully restrict root), pre-existing symlink at `<report-dir>/pipeline_report.json` (refused; unrelated symlink target preserved byte-identical; no PPTX written), pre-existing read-only `<report-dir>/pipeline_report.txt` (refused; prior content preserved byte-identical; auto-skipped under root), happy-path `--report-dir` outside the workspace writes `pipeline_report.json` + `pipeline_report.txt` with `overall_ok=true`, pre-existing symlink at `--output`, pre-existing directory named `*.pptx` at `--output`, `validate_workspace` failure cascading `[SKIP]` across every downstream stage, and a prior regular `.pptx` preserved byte-identical when `validate_workspace` fails before export. Stage 1 (Intake) is now automated by `scripts/init_workspace.py`: it seeds a brand-new workspace from a single local `.md` / `.txt` source by writing `<workspace>/input/source.md` + `<workspace>/source_manifest.json` (schema-backed against `schemas/source_manifest.schema.json`). Stage 2 (Brief) has **narrow contract support** via `scripts/init_deck_brief.py`: from a stage-1 workspace plus explicit `--title` / `--audience` / `--objective` (and optional `--tone` / `--language` / `--approximate-slide-count`), the helper writes a minimal schema-valid `deck_brief.json` whose `source_refs` carries `source_manifest.source.id` — without extracting any business content from the source body, so it is NOT a full prompt/report-to-PPTX automation. Stage 3 (Plan) has **narrow contract support** via `scripts/init_deck_plan.py`: from a stage-2 workspace plus a `--plan-spec` JSON file describing the plan content, the helper validates the spec against `schemas/deck_plan.schema.json` and the planner-semantics cross-checks (planned-count equality, unique + contiguous slide indices, section coverage, slide.section_id resolution, slide.source_refs subset of deck_brief.source_refs) and writes `<workspace>/deck_plan.json` — without extracting any business content from the source body, so it is also NOT a full prompt/report-to-PPTX automation. Stages 4–6 (Design system → per-slide Plans → Image manifest) remain agent-driven — the agent must produce `design_system.json`, `slide_plans/*.json`, and `image_manifest.json` according to the schemas under `schemas/` before `scripts/run_pipeline.py` will accept the workspace. The runner refuses any workspace whose stage-3-through-6 artifacts are missing or malformed via its first stage (`validate_workspace.py`).

## Adaptive planning

The Brief and Plan stages are **adaptive**, not template-driven:

- The Brief stage derives `deck_brief.json` from the user's request and the normalized source. It captures intent, audience, objective, and any explicit constraints (including `approximate_slide_count` if the caller supplied one). `source_refs` is required and non-empty: every brief lists the opaque source identifiers the deck draws from.
- The Plan stage chooses, for that specific brief: **target slide count**, **section structure**, **which layouts each slide uses**, and **per-slide density**. There is no universal sequence — agenda, section dividers, KPI dashboards, timelines, and conclusion slides are tools the planner *may* use, not slots it *must* fill.
- Expected capacity range is **12–25 slides** as guidance; a real run may produce 6, 8, 10, 15, 20, 25, or another reasonable count. The number depends on the brief, not on the template.
- Different scenarios produce different shapes — e.g. executive summary, product proposal, technical solution, project review, research report, training deck, strategy memo. Template families exist to provide the layout vocabulary; they do not dictate slide count or order.

### Planner contract (machine-enforced)

`deck_plan.json` carries a stricter planner contract that the validators cross-check, while still imposing **no** maximum slide count or required layout sequence:

- `deck_plan.planning.planned_slide_count` must equal `len(deck_plan.slides)`.
- `deck_plan.planning.rationale` is a required short string explaining the planner's length / structure choice.
- `deck_plan.sections[]` (`id`, `title`, `summary`, `slide_indices`) partitions the deck: the union of every section's `slide_indices` must equal the set of `slides[].index` values — no duplicates across sections, no missing deck indices, no orphan section indices.
- Each `slides[]` entry carries `section_id` (must exist; the slide's index must be listed by that section), `summary`, `density` (`low` / `medium` / `high`), and a non-empty `source_refs` whose values must all be declared in `deck_brief.source_refs`.

See `references/slide-contracts.md` and the schemas under `schemas/` for the authoritative shape; `references/quality-gates.md` lists the matching gates.

## Invariants

- Stage `n` may not start until stage `n-1` has produced its output and that output has passed schema validation.
- `deck_plan` must exist before any render-model or SVG work. Per-slide plans must exist before that slide's render model. A slide's render model must exist before that slide's SVG and before its PPTX shapes are emitted.
- The render model is the **only** input to the SVG renderer and the PPTX exporter — neither stage may read `slide_plan.json` directly, so the controlled primitive contract cannot be bypassed.
- SVG is a required **preview / inspection artifact and validation gate** for every slide, not the source language for PPTX. The PPTX exporter does **not** parse SVG; it builds native PowerPoint objects from the same `render_model.json` the SVG renderer consumed. This repo is intentionally not a broad SVG → PPTX converter.
- The terminal output is an **editable** PPTX.

## Project workspace

Each run uses a workspace directory chosen by the caller. All intermediate artifacts live there. The skill must not hardcode `projects/<name>`; the path is always passed in.
